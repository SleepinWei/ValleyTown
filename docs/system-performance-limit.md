# Jev + DeepSeek 系统阶梯压力测试

测试日期：2026-09-27。24 名可行动成年人，真实模型 API，独立 Worker，起点为同一存档的游戏分钟 6956.392331。完成 8 个约 45 秒窗口，采样总计 361.832 秒、2,377 次 HTTP 尝试。全部测试已停止，8 个测试账本均无 pending 请求。

结论：本轮最高平均时钟推进为 **114.08×**，最高单窗口行动吞吐为 **13.54 次/秒**，但没有验证出可稳定保持的最高倍率。48× 两次运行分别达到 **45.78×** 和 **13.36×**；后一次大部分时间等待全局同步。高倍率也显著减少了每游戏小时的角色活动，不能把时钟速度视为完整模拟性能。

## 条件与计量

- 在隔离代码副本中将速度参数验证上限从 6× 放开到 192×；界面和生产服务保持原样。
- 保留 Jev / DS 分工、提示、动作候选、执行校验、1.5 秒单角色自动行动节流，以及 12 / 3 / 4 行动／对白／后台并发池。
- 每档从同一 SQLite 快照独立开始，先按 6、12、24、48、96、192× 升序测试，再复测 48×、补测 72×。各窗口均以时长结束，没有预算中断。
- 250 ms 采样；使用轻量计数记录 tick 耗时、进程 CPU 和同步等待。结束时保留在途调用的费用与未知预留。
- 每组时间约 45 秒，属于短时阶梯测试，并非长时间稳定性验收。按升序测试也存在网络时段和缓存预热偏差。
- 使用 90% 目标达成率作为一个描述性指标，不把它当成人物行为质量或长期稳定性保证。
- 没有浏览器渲染负载，不测 FPS；本结论针对 24 人真实模型后端，不代表任意人口规模。

|---|---:|---:|---:|---:|---:|
| 6× | 4.90× | 2.87 | 1.471 秒 | 15.5% | 14.21 |
| 12× | 6.72× | 3.71 | 0.858 秒 | 43.0% | 13.79 |
| 24× | 6.75× | 3.04 | 1.439 秒 | 70.6% | 12.07 |
| 48×，首次 | **45.78×** | **13.54** | **0.572 秒** | 5.2% | 8.12 |
| 96× | 62.42× | 9.59 | 0.901 秒 | 35.9% | 5.05 |
| 192× | **114.08×** | 9.37 | 2.075 秒 | 41.8% | 2.95 |
| 48×，复测 | **13.36×** | 3.09 | **6.785 秒** | **71.2%** | 5.58 |
| 72×，补测 | 13.36× | 1.57 | 7.536 秒 | 80.4% | 3.85 |

“行为生效”是 `appliedAt - queuedAt`，从记录可调度状态到后端提交行动，包含排队、判断、重试和本地提交。只统计已应用的动作，含规则覆盖；失败和暂停暂存不伪造生效时间。它不包含此前的持续活动、调度冷却，也不包含浏览器显示或活动最终完成时间。少数未完成请求可能冻结全镇，因而表中较好的生效 P95 不能排除严重的全局等待。

“本地活动完成”仅为工作、阅读和休息结算事件之和；户外事件同时包含出发、开始和完成，未混入该指标。计数包含起点已开始的活动。不同模型选择和覆盖的游戏时段不同，活动密度降低是本次观察，不是严格同轨迹的因果估计。

同步占比包含已结束的同步段，以及最后一次采样中尚未结束的同步等待，未结束部分有采样误差。不能把剩余的所有倍率损失都归因于 CPU。

## 测到了哪些上限

### 1. 时钟推进：最高测到 114.08×，不是绝对极限

192× 档折合约现实 **15.8 秒 / 游戏日**，但只完成目标的 59.4%。测试没有继续提高到 384× 或更高，因此不能说 114.08× 是数学或硬件上限。更重要的是，此时本地活动密度比本轮 6× 档低约 **79%**。每游戏小时费用虽然降低，也伴随行为密度下降，不能称为等质量的成本优化。

### 2. 自动行动吞吐：本轮峰值约 13.54 次/秒

首次 48× 档在 45.213 秒内提交 612 次行动，其平均吞吐为 13.54 次/秒。当前 24 人，每人约 1.5 秒才能再次启动自动下一步选择，因此此类自动选择的结构性上限约为 **24 / 1.5 = 16 次/秒**。这是按现有节流规则推算，不是供应商 API 峰值，且不包含独立社交等其他判断。移动、持续任务、同步等待与请求失败会进一步降低实际值。

提高游戏倍率并没有提高这个每现实秒的调度上限。96×、192× 的行动吞吐反而约为 9.6、9.4 次/秒，同时每游戏小时的行为更少。因此当前系统并不是仅把速度参数调大就能等比例运行更多完整行为。

### 3. 稳定倍率：本轮没有确认

48× 首次达到目标的 95.4%，是首轮唯一达到 90% 目标的档位；复测却仅达到 27.8%。不能依据第一次结果宣称系统稳定支持 48×。同样，12× 和 24× 较差并不说明它们物理上无法运行，而是这些短窗口被长请求影响。

本轮 6× 平均为 4.90×，也低于此前不同窗口的 5.39×，进一步说明真实网络与服务延迟必须纳入长期速率判断。当前界面仍保留 6×，本测试没有自动上调生产上限。

## 主要瓶颈

1. **模型请求长尾被全局同步放大。** 12× 和 24× 都在游戏分钟 7199.999999 的跨日边界等待。12× 出现约 44.7 秒和 12.1 秒的用量未知调用；24× 约 70.6% 的窗口在同步等待。48× 复测也出现用量未知请求和多次连接前失败，其同步等待达 71.2%。
2. **角色固定调度节流限制了行动密度。** 提高游戏时钟不会缩短 1.5 秒的现实调度间隔。在较高倍率下，同一个角色两次选择之间可能已过去大量游戏时间。
3. **瞬时行动池拥堵在高档位开始明显。** 192× 行动排队 P95 为 1.257 秒；72× 补测遇到连接故障时达到 7.206 秒。首次 48× 仅为 1 ms，因此继续堆并发并不能解释或解决所有档位的问题。
4. **未观察到持续 CPU 饱和。** 各窗口进程 CPU 平均约占单核容量的 9%–29%；大部分档位 tick 平均约 3–7 ms。首轮 6× 有一次约 1.08 秒的同步 tick 停顿，说明偶发本地阻塞也存在，但不支持“CPU 已跑满”作为主要结论。tick 统计不包含所有异步回调工作，不能独立用于整机性能定性。

在不稀释角色行为的前提下提高速度，应先处理长尾请求和同步依赖，再评估单角色调度节流与活动意图复用。仅放开 UI 倍率上限，会把时钟推进能力与角色行为处理能力混为一谈。本次只测量，没有实施这些优化。
