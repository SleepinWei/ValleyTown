数据截取：2026-09-27 18:14:43，北京时间。只读本地 SQLite 账本及已有性能采样，没有启动游戏或产生新模型调用。截取时游戏暂停，行动／对白／后台在途数均为 0。

## 统计口径

- 每条 `calls` 是一次 HTTP 请求尝试，重试单独计数，不能直接等同于独立 Agent 决策。
- 累计包含历史版本、烟雾测试和对照实验，并非当前版本每分钟的消耗。
- `complete` 代表接口成功返回并结算用量，不代表动作最终获准执行。
- `failed` 代表已确认未执行或接口明确拒绝；`unknown` 代表结果／用量待核对，保留预留额度，不当作免费失败。
- 时间轴是请求发起的现实时间；请求结束由 `created + latency` 估算。无法从历史账本可靠还原所有请求的游戏时间、连接阶段耗时、未知请求实际结束时间或关键屏障原因。
- 分位数使用 nearest-rank（向上取整）；与之前性能报告按向下取整计算的 P95 有轻微差异。

## 建议按以下顺序加速

### 1. 让 Jev 批准完整的活动意图，而不只批准目的地

例如一次选择「去图书馆阅读 20 游戏分钟」，保存意图、目的地、有效期限及中断条件。抵达时同步校验天气、资源、开放时间和角色状态；仍满足条件则执行已获批准的动作。只有目标失效、重要变化或产生新的选择时重新调用 Jev。社交、婚姻和资源竞争仍需双方决定与提交校验。

先做较小改动也可：在快速上下文里加入结构化到访目的、上一地点与最近两次行动，提示模型识别往返循环；不会强制角色工作或禁止合理移动。再用同一存档和相同场景验证往返次数、有效活动完成数、每游戏小时调用量与实际倍率。

这是当前优先级最高的方案：同时减少模型请求、空走和 token 消耗。潜在收益明显，但不能从 13 秒数据直接承诺减少百分之多少。

### 2. 局部关键节点只同步相关请求

当前发现任一相关活动即将结算后，会等待所有行动／对白／后台任务结束。可以改成：本地活动、约会等节点只等待相关居民或共享资源的依赖请求；跨日、全局天气切换仍全镇同步。无关居民的慢请求不再拖住另一个居民的局部结算，关键条件仍在提交前同步校验。

先补充轻量日志：屏障原因、游戏时间、开始／结束现实时间、依赖的请求 ID、阻塞时长。没有这项记录，就难以判断局部同步究竟省了多少时间。

### 3. 处理长尾连接失败，而不是继续堆并发

本轮长行动的 8.25 秒由连接失败、重试等待和后续请求组成，远高于成功请求的 0.462 秒中位数。保留连接复用；分别记录建连、首字节、完整响应与重试时间。对明确未发出的建连失败考虑更早回退；对于已经发出、只是未收到结果的请求，仍保留用量预留，避免盲目重复发送。

当前 Jev 上限 12、DS 后台上限 4，平均在途只有 4.48／0.24，行动排队 P95 仅 2 ms。此样本不支持继续提升并发作为首选，也不支持优先合并 DS 请求。短测没有跨日规划高峰或完整对白负载，后续仍需覆盖这些情境。

### 验收指标

在相同起始存档与目标 6× 下比较：实际倍率、每游戏小时 Jev / DS 次数、有效活动完成数、往返循环数、被拒绝的旧决策数、同步阻塞秒数和 token 用量。仅游戏时钟接近 6×，但居民一直等待或空走，不能算有效提速。
